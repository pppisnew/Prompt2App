# ADR-0008：重构开始之前先建立评测集

- **状态**：Accepted
- **日期**：2026-06-18
- **决策者**：项目作者
- **相关 Phase**：Phase 0（地基）
- **相关 Issue / PR**：feature/ai-engineering-rebuild 首次提交

---

## 背景（Context）

本项目已识别出多项需要重构的内容：删除 LangChain4j 源码覆盖包、收敛微服务回模块化单体、重写 AI Router、改造 Tool Calling Agent、引入 Prompt 评测体系。

但这些重构都涉及 **AI 生成行为**——即给定相同的用户需求，重构前后输出可能在以下维度有差异：

- 生成是否仍能编译/运行
- 生成耗时与 Token 消耗
- 主观质量（视觉、交互完整性）
- Prompt 改写后的回归是否引入退化

**关键事实**：当前项目对上述 AI 行为**没有任何客观度量**。所有"代码改完后还能跑吗"的判断都依赖手工敲一两条 prompt 试一下。

这意味着在不建评测集的前提下做任何重构，本质上都是**赌博式重构**——改完之后无法证明"项目是变好了还是变坏了"。

---

## 备选方案（Options）

### 方案 A：先动代码，等遇到问题再补评测

- 优点：起手快，立刻能看到代码层面的进度。
- 缺点：
  - 重构过程中如果 AI 输出退化，无法第一时间发现，问题会被埋到下游。
  - 后续补评测集时，已经无法重建"重构前的基线"——基线丢失等于评测体系自废武功。
  - 写简历时无法用数据讲故事，只能讲"我重构了 X"。
- 长期成本：高。重构过程中累积的隐性退化最终会让 Phase 5（评测体系）变成救火，而非演进。

### 方案 B：先建评测集 v0（YAML cases + 手跑基线），再开始所有代码改动

- 优点：
  - 重构前的基线被冻结（基线分数、产物快照），后续每个 Phase 都可以对比。
  - 评测集本身是 Phase 5 的输入，提前建立等于把核心资产提前做出来。
  - 写简历时可以说"重构后编译成功率 X%→Y%、单次成本 X→Y"——**全是数字**。
- 缺点：
  - 起手 2 天看不到代码层面的进度，心理上会有挫败感。
  - 评测集 v0 的设计本身需要思考（case 选取、评分维度），不是无脑工作。
- 长期成本：低。评测集是后续所有 Phase 的基础设施，越早建越值钱。

### 方案 C：边重构边建评测，每个 Phase 配 5 个 case

- 优点：进度看得见，评测集渐进式增长。
- 缺点：
  - 不同 Phase 写的 case 风格不统一，会变成"5 个一组的小评测集"而非一套体系。
  - 早期 Phase 没有完整评测集保护，仍然是赌博式重构。
- 长期成本：中。最终评测集会因风格不一致需要返工，反而比方案 B 更费时间。

---

## 决策（Decision）

**选择方案 B**：在动任何业务代码之前，先一次性建立 v0 评测集，并跑通基线。

**v0 的范围**：
- 25 个 YAML 格式的 case，按难度 / 策略分布：HTML 7 条、MultiFile 8 条、Vue 10 条。
- 每个 case 包含：用户 prompt、期望策略、关键评分点（必须包含的元素 / 必须避免的反模式）。
- 在重构前用现版项目跑完一遍，记录基线指标到 `eval/reports/baseline.md`。

**关键约束**：
- 项目目标是作品集而非 SaaS，因此评测维度限定为 **3 维**：编译成功 / 页面渲染非空 / LLM-as-Judge 主观分。**不做**视觉相似度、Lighthouse、a11y 等镀金维度。
- 评测集 v0 由人工编写而非 LLM 生成，避免与生成端使用同源模型导致的偏差。

---

## 代价（Consequences）

### 正面

- 后续每个 Phase 都能用数字证明"是否退化"。
- ADR-0005（评测体系）的实施成本被显著降低——届时只需补自动化与 CI 集成，case 已就位。
- 简历可以包含具体数字（编译成功率、平均耗时、Token 成本），而非定性描述。
- 写 case 的过程会强制重新理解项目的产品边界，反哺架构理解。

### 负面

- Phase 0 的 2 天工时在外部看来"没产出代码"，可能被低估。
- v0 评测集只有 25 case，覆盖率有限，无法捕捉所有退化模式（例如长 prompt、多轮对话等）。
- 跑基线时需要至少调一次现版的 AI 接口，会产生少量 Token 成本（按 DeepSeek 估算 < $0.5）。

### 中性

- 评测集格式（YAML）锁定后，后续扩充到 50/100 case 时不需要变更 schema。
- LLM-as-Judge 的评分稳定性需要后续观察；如果发现波动 > 10%，需要在 ADR-0005 中重新讨论。

---

## 复盘指标（Revisit Triggers）

满足下列任一条件时，应重新评估本决策：

- 评测集 v0 落地后，发现 25 case 不足以反映真实退化（例：3 次重构后基线分数与主观体验脱钩）。
- LLM-as-Judge 评分波动超过 10%，需要引入更稳定的评分机制（例：多次平均、多模型仲裁）。
- 项目目标从"作品集"切换为"对外服务"，需要追加视觉相似度、a11y 等维度。
